# PPC (Product Problem Clear) 프로토타입

생산관리자가 부품 재고와 발주를 한 화면에서 확인하고, 부품 공급에 차질이 생기면 대체 업체와 그 결과를 바로 비교해 결정하는 웹 프로그램입니다. 팀 ICBM · 설계 기준은 [docs/DESIGN.md](docs/DESIGN.md)(설계서 v0.2)입니다.

## 실행

**가장 쉬운 방법**: `ppc` 폴더의 **`start-ppc.bat`**(Windows)을 더블클릭합니다. 처음이면 패키지를 설치하고, 개발 서버를 띄운 뒤 브라우저를 자동으로 엽니다. Node.js가 없으면 설치할지 물어봅니다. macOS는 `start-ppc.command`를 씁니다.

직접 실행하려면 Node.js 22.12 이상이 필요합니다. (없으면 `winget install OpenJS.NodeJS.LTS`)

```bash
cd ppc
npm install
npm run dev        # http://localhost:5173
```

| 명령 | 하는 일 |
|---|---|
| `npm run dev` | 개발 서버 |
| `npm test` | 단위 테스트 (설계서 §9 기대값, 저장 흐름, 대시보드 값) |
| `npm run build` | 타입 검사 + 배포용 빌드 (`dist/`) |
| `npm run data` | `data/ppc_data.xlsx` → `src/data/reference.json`, `employees.json` 다시 만들기 (Excel을 고친 뒤 실행) |
| `npm run qr` | 발표용 QR 무늬 → `src/data/qr.json` 다시 만들기. 배포 주소가 바뀌면 `npm run qr -- https://새주소/` |

## 저장 방식: 공유 DB / 로컬 데모

상단 바의 배지로 지금 어느 쪽인지 알 수 있습니다.

- **공유 DB** — `.env.local`에 Supabase 값이 있을 때. 같은 주소를 연 사람은 모두 같은 데이터를 봅니다(캠프 완성 기준).
- **로컬 데모** — 값이 없을 때. 이 브라우저(localStorage)에만 저장하고, 처음 열면 시연 데이터가 자동으로 들어갑니다. 다른 사람과 공유되지 않습니다.

### Supabase 연결 (설계서 부록 C-1)

1. Supabase 프로젝트를 만들고 SQL Editor에서 [supabase/schema.sql](supabase/schema.sql)을 실행합니다. (이미 만든 프로젝트라면 [supabase/migration_activity_log.sql](supabase/migration_activity_log.sql)만 실행)
2. `.env.example`을 `.env.local`로 복사하고 두 값을 채웁니다.
   ```
   VITE_SUPABASE_URL=https://xxxx.supabase.co
   VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
   ```
   secret key(`sb_secret_…`)는 절대 넣지 않습니다. `.env.local`은 커밋하지 않습니다.
3. 개발 서버를 다시 시작하고, 화면의 **[시연 데이터 넣기]**(또는 [데이터 초기화])를 한 번 누릅니다.

### Vercel 배포 (설계서 부록 C-3)

- Root Directory: **`ppc`** (앱이 저장소의 하위 폴더에 있습니다)
- Framework Preset: Vite · Build Command `npm run build` · Output Directory `dist`
- Environment Variables에 위 두 값을 같은 이름으로 넣습니다. 값을 바꾸면 Redeploy해야 반영됩니다.
- `vercel.json`이 있어 `/disruptions/D-001` 같은 주소를 새로고침해도 404가 나지 않습니다.

### 3D 차량 뷰어

저장소 루트 `car-manager/`의 3D 스튜디오(three.js)를 대시보드의 '부품 재고' 영역으로 옮겼습니다. BOM 7개 부품(엔진·변속기·브레이크·서스펜션·조향·차체·배터리)이 핫스팟으로 붙어 있고, 누르면 그 부품으로 줌인하면서 재고·입고 현황 카드가 뜹니다. 부품 상태(차질 빨강 / 대응 중 파랑 / 주의 주황)는 핫스팟의 점과 해당 부품 메쉬의 색으로 표시됩니다. WebGL을 쓸 수 없는 브라우저에서는 도면 이미지로 대신합니다.

## 설계서와 다른 점 · 덧붙인 점

- **로컬 데모 모드** (설계서에 없음): Supabase 값이 없어도 앱을 띄워 볼 수 있게 넣었습니다. 공유가 필요한 시연에서는 반드시 Supabase를 연결하세요.
- **3D 차량 뷰어** (설계서에 없음): `car-manager`의 화면을 반영해 달라는 요청으로 추가했습니다. 이 때문에 `three`(r128 고정, car-manager와 같은 버전)가 의존성에 들어갑니다.
- **조사 처리**: 문구 T3의 `{부품}을`과 취소 경고의 `{부품}이`는 받침에 따라 을/를, 이/가를 고릅니다(예: "배터리를"). 엔진·조향처럼 받침이 있는 부품은 설계서 예문과 똑같이 나옵니다.
- **기간 내 미완료 주문**: 고객 안내 문구(T5)는 `lateDays > 0`인 주문만 만들고, 예측 기간 안에 끝나지 않는 주문은 안내 문구 대신 경고 한 줄을 보여 줍니다.
- `applyOriginalPoAction`은 어느 차질의 지연 발주인지 알아야 해서 `disruptionId` 인자를 하나 더 받습니다.

## v0.2 이후 추가된 규칙 (설계서에 없는 것)

- **기준일은 항상 오늘**: DB의 `base_date`가 아니라 화면을 연 기기의 오늘 날짜를 씁니다. [데이터 초기화]는 시연 데이터의 날짜(발주일·도착 예정일·납기)를 오늘에 맞춰 옮깁니다. 리허설에서 날짜를 고정하려면 환경 변수 `VITE_BASE_DATE=2026-10-05`를 줍니다.
- **사원번호 권한**: 발주, 대체 발주 확정, 발주 취소, 납기 추가·취소, 데이터 초기화는 Excel '발주권한자' 시트(발주 권한 Y)에 있는 사원번호를 입력해야 합니다. 권한은 하나이며 나누지 않습니다. 테스트용 사원번호 `0000`은 Excel과 상관없이 항상 통과합니다(`src/lib/employees.ts`).
  - 화면에서 하는 확인이라 실수 방지용입니다. 명단이 앱에 들어 있고 DB는 열려 있으므로 보안 장치는 아닙니다.
  - 사원번호 입력칸은 비밀번호처럼 가려집니다(●●●●). 발표 화면에 번호가 비치지 않게 하려는 것이고, 번호가 맞으면 아래에 이름·부서만 나옵니다. 이력의 '입력자' 칸에는 `이름(사원번호)`가 그대로 남습니다.
- **QR 접속 페이지**: QR 무늬는 `qrcode-generator`(개발용 의존성)로 미리 만들어 `src/data/qr.json`에 넣어 둡니다. 화면은 그 파일만 읽으므로 배포되는 앱에는 라이브러리가 들어가지 않습니다. 오류 복원 수준 Q, 29×29칸, 둘레 여백 4칸, 순수 검정/흰색입니다.
- **발주대기 / 발주 취소**: 발주한 당일의 일반 발주는 이력에서 '발주대기'로 보이고 그날까지만 취소할 수 있습니다. (DB에는 '입고대기'로 저장하고 화면에서만 구분합니다.)
- **업체별 발주 한도**: 한 업체에 일반 발주로 넣을 수 있는 수량은 일주일 동안 50개입니다. 발주일로부터 7일이 지나면 풀립니다. 시연 초기 발주와 대체(긴급) 발주는 한도에 넣지 않습니다. 기준값은 `src/lib/constants.ts`에 있습니다.
- **부품 주의사항**: Excel '주의사항' 시트를 읽어 3D 뷰어의 부품 상세에서 [주의사항] 버튼으로 보여 줍니다.
- **출차 일정 · 수리 차량 페이지**, **납기 추가 · 납기 취소**.

### Excel (`data/ppc_data.xlsx`)

`자동차부품_생산관리_가상데이터_업체별단가추가` 워크북의 사본이고, **이 파일 하나만** 씁니다(다른 Excel 파일은 쓰지 않습니다). Excel을 고친 뒤에는 `npm run data`를 실행합니다.

| 시트 | 쓰는 곳 |
|---|---|
| 생산제품 · 제품별_자재 · 자재 · 공급업체 | 부품, 소재 필요량, 업체(납기·월 공급가능량·납기 준수율). 준수율은 모든 업체가 93%라 등급은 전부 '보통'이고 '위험' 업체는 없습니다(위험 업체를 뒤로 미는 로직은 그대로 있습니다). |
| 업체별_자재단가 | **발주 금액** = 업체의 자재 단가(원/kg) × 부품 1개당 소재 필요량(kg) × 수량. 금액은 DB에 저장하지 않고 Excel 단가로 계산합니다. |
| 지연시간 | **수량에 따른 납품 지연**. 도착 예정일 = 기준일 + 업체 기본 납기 + 지연(1개 / 10개 / 50개 단계, 같은 업체·같은 부품의 최근 일주일 수량을 합쳐서 판단). 대체(긴급) 발주와 정기 계약 물량에는 적용하지 않습니다. |
| 차량색상 | **색상별 차체**. 이 시트의 색상마다 차체가 한 종류씩 생깁니다(`P012-C01` …). 색마다 따로 재고를 관리하고 따로 발주·입고·소모하며, 차 한 대에 그중 하나가 들어가 그 차의 색이 됩니다. 시트에 색을 더하거나 빼면 차체 종류도 따라 바뀝니다(초기 재고는 `demo_state.json`의 `bodyStock`). 화면의 색 견본은 색 이름으로 정합니다(`components/ui.tsx`). |
| 발주권한자 | 사원번호 권한 확인 |
| 주의사항 | 부품 주의사항 |

지연 사례(예전 Excel의 '지연상황_예시')는 새 파일에 없어서, 차질 발생 창의 버튼은 시연 데이터(`demo_state.json`의 `disruptionExamples`)의 '시연 예시'로 바꿨습니다.

## QA 보고서 반영 (`PPC_QA_테스트보고서.md`)

- **모든 저장 작업에 사원번호** (BUG-006·008·018): 발주, 발주 취소, 차질 등록·지연 연장, 대체 발주 확정, 기다리기, 해결, 입고 처리, 납기 추가·취소, 생산 설정, 데이터 초기화.
- **확인 창은 앱 자체 모달** (BUG-019): 브라우저 기본 `confirm()`을 쓰지 않습니다(`EmployeeConfirmModal`). 확인 창에서 사원번호를 함께 받습니다.
- **활동 기록** (BUG-005·021): 저장할 때마다 누가·언제·무엇을 했는지 `activity_log` 테이블에 남기고 이력 페이지에서 봅니다. 납기 취소도 여기에 남습니다. **이미 만든 Supabase 프로젝트에는 [supabase/migration_activity_log.sql](supabase/migration_activity_log.sql)을 한 번 실행해야 합니다.** 실행 전에도 앱은 동작하지만 기록이 저장되지 않고, 이력 페이지에 안내가 뜹니다.
- **중복 발주 방지** (BUG-001): 저장 중에는 두 번째 클릭을 무시하고, 같은 날 같은 부품·업체·수량의 발주가 이미 있으면 확인란에 표시해야 들어갑니다. 번호가 다른 사람과 겹치면 새 번호로 다시 시도합니다.
- **공급 능력** (BUG-003·009): 남은 능력 = 월 공급가능량 − 최근 30일 동안 그 업체에 발주한 양(kg). 넘으면 일반 발주도 대체 발주도 막습니다. 정기 계약 물량(시연 초기 발주)은 세지 않습니다.
- **지연 연장** (BUG-004): 같은 부품·업체에 해결되지 않은 차질이 있으면 새 차질을 만들지 않고 그 차질의 지연일수를 늘립니다.
- **실제 도착일로 해결** (BUG-005): [해결 완료]에서 지연되던 발주가 실제로 들어온 날짜를 받습니다. 오늘 이전이면 입고 처리(재고 반영), 내일 이후면 그 날짜로 확정하고 예측을 다시 계산합니다.
- **대체 추천 수량** (BUG-007): 설계서의 `지연일 × 일일 투입 × 대당 수량` 대신 '지연된 발주가 올 때까지 모자라는 양(재고와 다른 입고 예정분을 뺀 값)'을 씁니다. 그래서 시연 예시의 추천 수량이 설계서 §9와 다릅니다(서스펜션 560 → 520, 엔진 100 → 80, 조향 120 → 80). 0이면 '대체 발주 불필요'로 안내합니다.
- **분할 발주**: 대체 수량이 업체당 한도(50개)를 넘으면 순위대로 여러 업체에 나눠 발주하는 계획을 추천하고, 확정하면 업체마다 대체 발주가 따로 생깁니다.
- **추천 후보** (BUG-011): 진행 중인 차질이 있는 업체와, 지연된 원래 발주보다 늦게 오는 업체는 뺍니다. 문구는 '동일 사양'이라고 단정하지 않습니다.
- **상한** (BUG-008·010): 수량 100,000, 일일 투입 1,000대, 리드타임 30일. DB 오류는 알기 쉬운 문구로 바꿔 보여 줍니다.
- **상태 이름 통일** (BUG-013): 발주한 당일의 일반 발주는 대시보드와 이력 모두 '발주대기'.
- **납기 추가 경고** (BUG-014): 저장 전에 예상 완료일을 계산해, 납기를 못 맞추거나 다른 주문을 밀어내면 경고합니다(추가는 가능).
- **차량 고유번호** (BUG-015): 전체 순번이 아니라 '주문 + 그 주문 안에서의 순번'으로 정해, 다른 주문이 끼어들어도 바뀌지 않습니다.
- **수리용 재고** (BUG-016): 수리 차량에 쓸 부품은 재고에서 따로 잡아 두고, 생산 가능 대수·재고 일수·생산 예측은 그만큼을 뺀 재고로 계산합니다. 초기 재고는 수리용을 포함한 값(엔진 61개 등)이라 생산 수치는 설계서와 같습니다. '부품 대기'는 재고로 계산합니다.

## 그 밖에 추가한 것

- **과거 기준 시연 데이터**: [데이터 초기화]를 하면 초기 발주·주문이 '오늘을 기준으로 지난 며칠 사이에 담당자가 입력한 기록'으로 만들어집니다(발주일·입력자·활동 기록 시각 모두 과거). 초기 발주는 입력자 끝에 '정기 계약'이 붙고 주간 한도·수량 지연·공급 능력 계산에서 빠집니다.
- **출차 실적**: 출차 일정은 기준일 이전 7일의 실적(하루 20대)과 기준일부터의 예정을 나눠 보여 줍니다.
- **예전 데이터 안내**: DB에 예전 형식의 데이터(색 구분 없는 차체, 오늘보다 뒤 날짜의 기록)가 남아 있으면 화면 위에 [데이터 초기화]를 하라는 안내가 뜹니다. **새로 배포한 뒤에는 한 번 초기화해야 합니다.**
- **발주 검색** (`/search`): 상단 검색창에서 부품·업체·소재로 찾아, 어느 업체에서 얼마에·며칠 만에·준수율 몇 %로 발주할 수 있는지 봅니다.
